# 02 — LLM Fine-Tuning (QLoRA)

Fine-tunes a small instruction-tuned model to reliably extract structured order data from messy natural-language text, using QLoRA (4-bit quantized LoRA) on a synthetic dataset.

## Task

**Input:** a natural-language sentence describing an order, in varied phrasing/currency/date format
> `"Aisha placed an order for 4 backpacks costing $3600, dated December 16, 2024"`

**Output:** structured JSON with exactly 5 fields
```json
{"customer": "Aisha", "item": "backpack", "quantity": 4, "amount": 3600, "date": "2024-12-16"}
```

## Why this task

Structured extraction from unstructured text is one of the more common real-world reasons small models get fine-tuned in production (parsing receipts, support tickets, emails into a system's data model). It also gives an unambiguous evaluation signal — a JSON output either matches the ground truth or it doesn't — instead of relying on fuzzy metrics like ROUGE/BLEU that don't really fit a correctness question.

## Data

Fully **synthetic**, generated by `src/prepare_data.py` rather than downloaded — a random order record (customer, item, quantity, price, date) is built first, then rendered into one of several natural-language sentence templates with randomized currency symbols and date phrasings. Because the ground truth is constructed before the sentence is, the correct JSON output is always known exactly, with no labeling ambiguity.

- 500 examples total: 400 train / 50 validation / 50 test
- Closed vocabulary: 16 customer names, 10 items — a deliberate simplification to keep this a small, fast demo rather than an attempt at open-vocabulary NER. A production version would need to generalize beyond a fixed list.

## Approach

| | |
|---|---|
| Base model | `Qwen/Qwen2.5-1.5B-Instruct` (same base model used across this portfolio's other projects) |
| Method | QLoRA — 4-bit NF4 quantization of the frozen base model, LoRA adapters trained in higher precision on top |
| LoRA config | r=16, alpha=32, dropout=0.05, targeting attention Q/K/V/O projections |
| Trainable params | 4,358,144 / 1,548,072,448 total (**0.28%**) |
| Hardware | Google Colab, free-tier Tesla T4 GPU |

QLoRA compresses the frozen base weights to fit comfortably in memory while training only a small set of low-rank adapter matrices (`r=16` here) — the original weights are never updated, which is why trainable parameters are under 0.3% of the model.

## Training results

| Metric | Value |
|---|---|
| Steps | 150 (6 epochs × ~25 steps/epoch, batch size 4 × grad accumulation 4) |
| Final train loss | 0.3835 |
| Final eval loss | 0.1942 |
| Mean token accuracy (eval) | 92.6% |
| Training time | ~21 minutes on a T4 |

Loss dropped steadily across training with no divergence, and the small dataset (400 examples) was enough for the model to reliably converge on the correct output format and field values, given the task's closed vocabulary.

## Before / after evaluation

Evaluated on 50 held-out test examples never seen during training. Since this is structured extraction, not free text generation, the metric is exact correctness rather than surface-level similarity:

- **parse_rate** — did the output parse as valid JSON at all?
- **exact_match** — did the parsed JSON exactly match ground truth on all 5 fields?
- **field_accuracy** — per-field correctness, for a more granular view than pass/fail

| Metric | Base model | Fine-tuned |
|---|---|---|
| Parse rate | 30% | **100%** |
| Exact match | 0% | **68%** |
| `customer` accuracy | 18% | **100%** |
| `item` accuracy | 6% | **100%** |
| `quantity` accuracy | 28% | **100%** |
| `amount` accuracy | 6% | **100%** |
| `date` accuracy | 10% | **68%** |

The base model, with no exposure to this exact output format, frequently failed to even produce parseable JSON (trailing commentary, malformed brackets) and almost never got every field right. After fine-tuning, every field except `date` reaches perfect accuracy on held-out data.

### Known limitation: the `date` field

`date` accuracy (68%) is the one field that doesn't reach 100%, and this is a real bug in the synthetic data generator, not a training shortfall worth glossing over. Two of the four date-phrasing styles used when generating input sentences (`"14 June"`, `"March 3rd"`) omit the year entirely — but the target JSON still requires a full year. For roughly half the dataset, the correct year genuinely cannot be inferred from the input text alone; the model is being asked to guess information that isn't there. A corrected version of the generator would either always include the year in the input phrasing, or drop year from the expected output when it's absent from the input.

## Setup

```bash
pip install -r requirements.txt
```

Requires a CUDA GPU (QLoRA's 4-bit quantization depends on `bitsandbytes`, which needs CUDA). This project was developed and run on Google Colab's free-tier T4 GPU rather than locally.

## Usage

```bash
# 1. Generate the synthetic dataset
python src/prepare_data.py --out_dir ./data --n_examples 500 --seed 42

# 2. Train LoRA adapters
python src/train_lora.py --data_dir ./data --output_dir ./adapter --config config.yaml

# 3. Evaluate base vs. fine-tuned
python src/evaluate.py --adapter_dir ./adapter --test_file ./data/test.jsonl --config config.yaml

# 4. Run inference with the fine-tuned adapter
python src/inference.py --adapter_dir ./adapter --prompt "Sana bought 3 mugs for ₹360 on July 4th"
```
